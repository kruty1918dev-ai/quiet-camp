# Генерація композиції за правилами

`CompositionGenerator` — переносне C# ядро без Unity, назв гри, рівнів або моделей.
Вхід: прямокутник захищеної гри, seed, стиль і впорядковані системи `ICompositionStage`.
Вихід: `CompositionPlan` з позами, власниками, діагностикою, derived seed,
оцінкою та історією всіх спроб.

## Контракти систем

1. **Layout**. `CompositionLayout` виводить базис камери, масштаб кадру, русло,
   профіль берега, рельєф і зону переходу з розміру поля. Відступ русла обчислюється
   з опорної функції прямокутника з урахуванням нахилу русла та максимальної амплітуди
   його вигину. Водойма не може проникнути в ігровий прямокутник.
2. **Crossing**. `CrossingStage` масштабує місток до ширини русла. Геометрія асета
   визначає його габарити й два контакти. Обидва кінці мають лежати на берегах.
   Після розміщення резервується прохід; інші системи не можуть зайняти його.
3. **Rocks**. Пакет `rock-placement` створює нерегулярні групи берегового каміння.
   Каміння осідає в поверхню; непридатні акценти відхиляються.
4. **Vegetation**. Пакет `vegetation-placement` отримує поля вологості й щільності.
   Великі дерева формують краї кадру, очерет росте на березі, квіти залишаються
   акцентами. Розміри, вага видів, інтервали та орієнтація належать профілю.
5. **Readability**. `ReadabilityRule` перевіряє проєкції всіх об'ємів кандидата
   відносно захищеної призми гри. Якір поза полем не дозволяє кроні закрити поле.
6. **Placement**. Усі системи делегують опору, нахил, просторові перетини й
   резервування єдиному `PlacementSolver` та його `PlacementContext`.
7. **Composition critic**. `CompositionCritic` рахує видимі силуети за ролями,
   їхню проєктовану площу, quadrants і баланс ліворуч/праворуч. Межі та ваги
   належать `CompositionReviewProfile`. Обов'язкові пороги відхиляють кандидата;
   серед прийнятих обирається найвища оцінка. При рівності виграє рання спроба.
8. **Host rendering**. Гра перетворює план на власні меші/префаби, воду, світло,
   вітер і постобробку. Тут немає залежності ядра від URP або комерційних асетів.

Порядок: структура → місток → каміння → дерева → очерет → квіти → native render.
Великий об'єкт резервує простір раніше за дрібні деталі. Паралельні мутації
контексту не підтримуються; порядок входить у контракт відтворення.

## Детермінізм і повторні спроби

Стиль, запит, critic rules і габарити асетів копіюються перед генерацією. Ідентифікатори та seed визначають
розміщення; камера/чанк не споживає випадковий потік. При обов'язковій помилці
наступна спроба створює новий контекст, а не дописує до старого. Ліміт спроб
належить стилю. З critic перебирається весь бюджет і обирається найкращий
допустимий план; без critic збережено попередній режим first-valid.
Скасування не публікує частковий план. `Ok` означає проходження налаштованих
геометричних і композиційних правил, а не автоматичне схвалення краси кадру.
`attempts` записує geometry/quality result, seed, score, metrics та причини
відмови для кожного кандидата. Не можна приховувати відмову зменшенням порогів
під час генерації. Всі невдалі спроби повертають явний відхилений план.

Відтворення вимагає тих самих версій коду, профілю, геометрії моделей та seed.
Різні рушії/GPU можуть давати різні пікселі при тому самому плані.

## Адаптація іншої гри

Передайте власний захищений прямокутник і `AssetShape` з реальних габаритів,
контактами та запасом для анімації. Замініть стилістичний профіль і rendering
adapter. Додаткові системи реалізують `ICompositionStage`; вони отримують уже
розраховані поверхню, водойму та резерви. Не копіюйте координати конкретного
кадру в систему і не намагайтесь генерувати gameplay через scenery.

Поточний layout підтримує ортографічну камеру та прямокутну гру. Інші топології
потребують окремого layout, surface query і правила захищеної проєкції.

## Приймання

`dotnet run --project Tests~/Contracts.csproj` перевіряє ядро на .NET 8.
291 перевірка композиції охоплює 48 комбінацій розміру/seed, контакти містка,
повторюваність, неправильні дані, скасування та закриття поля високою кроною.
Окремо тестуються ecological/rock adapters у відповідних пакетах.

Для візуального приймання потрібен рендер у цільовій грі, перевірка проходів,
силуетів, тіней, дрібних деталей і крайових кадрів. Порівняння з референсом та
людське рішення залишаються окремим кроком. Піксельної тотожності AI-ілюстрації
ці геометричні перевірки не доводять.

`CompositionCritic` використовує проєкції габаритів, а не rendered pixels.
Projected area — сума clipped rectangle areas; це proxy щільності, не точна
кількість зайнятих пікселів. Score 0.9 не означає 90% схожості з референсом.
Матеріали, світло, тіні, aliasing та анімація потребують native перевірки.

## Виконувана перевірка переносності

У [CompositionGallery](../Samples~/CompositionGallery/README-UA.md) той самий
pipeline компілюється без Unity/QuietCamp. Два JSON host profiles міняють
asset IDs, габарити, ecological rules та контекст (сад / промисловий двір).
Plan export та повторний replay перевіряються як непорожні JSON artifacts.
Це доказ роботи host boundary, а не native художнє приймання іншої гри.

Покриття поверхні перевіряється для minimum/nominal/maximum aspect; viewport
не повинен показувати край світу. CrossingStage також резервує проєкцію
містка через `ProtectVisibility`; наступна рослинність не може перекрити його
силует навіть без фізичного зіткнення. Інші stages можуть явно захищати
власні ключові структури тим самим API.
