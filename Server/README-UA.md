# Сервер Quiet Camp — підготовка без розгортання

Цей каталог не входить до Unity Assets. Сервер не розгорнуто. Реальні покупки,
Google credentials, продукт Play та production endpoint не надані.

`service.py` надає WSGI-застосунок: `POST /v1/purchases/verify`,
`POST /v1/play/notifications` і вимкнений за замовчуванням `POST /v1/metrics`.
Тести не потребують Google credentials: `python -m unittest discover -s Server -q`.

## Необов'язковий безоплатний Pro

`POST /v1/access/sign-in` приймає `packageName`, `username`, `password`;
`POST /v1/access/refresh` — `packageName`, `sessionToken`. Обидва повертають
вузьку область `scope=pro`, package/product і право на 24 години. Відсутня
серверна конфігурація дає 503, неправильні дані — 401 без їхнього відображення.
Пароль не має строку дії, одноразового коду чи геообмеження. Нових користувачів
ці endpoints не реєструють. Товар Play і його квитанції для них не потрібні.

Підготуйте окремі дані командою
`python Server/provision_complimentary_access.py --output <private-directory-outside-repository>`.
Інструмент не перезаписує існуючі дані та не вмикає доступ. Приватний JSON
призначений для полів Play Console після перевірки; `.private.env` містить
`QC_COMPLIMENTARY_USERNAME` і PBKDF2-хеш для сервера. Не кладіть ці файли в Git.
Без них доступ вимкнений. Сесії зберігаються хешованими у тому самому SQLite;
неактивні 90 днів очищуються під час наступного входу. Обмежте auth-запити на
ingress, вимкніть body/header logging, забезпечте HTTPS і постійний диск.
Зміна серверного хешу відкликає старі сесії при повторній перевірці.

Повний статус та інструкції: [Config/PLAY-REVIEW-UA.md](../Config/PLAY-REVIEW-UA.md).

## Підготовка середовища власником

1. Створіть окремий backend-проєкт/службову ідентичність. Увімкніть Google Play
   Developer API, надайте лише потрібні права на конкретний додаток у Play Console.
   Використовуйте workload/service identity та Application Default Credentials.
   Не завантажуйте приватний service-account JSON у гру, Config або Git.
2. Створіть Python venv, установіть `Server/requirements.txt`. Перенесіть назви
   змінних з `env.example` у захищене серверне середовище. Якщо інфраструктура
   все ж потребує секретів, використовуйте Secret Manager та ротацію.
3. Підготуйте захищений постійний диск для SQLite, каталог із правами 0700,
   резервування та контроль доступу. Файл отримує 0600 на POSIX. Для кількох
   вузлів потрібна спільна транзакційна БД; цей варіант розрахований на один вузол.
4. Після окремого дозволу на deployment запускайте WSGI через gunicorn,
   наприклад `gunicorn --workers 1 --threads 4 Server.service:application`.
   Не запускайте цей приклад як частину prepare. Завершуйте TLS на ingress;
   вимкніть запис body, Authorization, query strings та ідентифікаторів/IP для
   metrics. Додайте rate limits і максимальний розмір запиту 16 KiB на ingress.
   Сам сервіс також обмежує розмір, типи й allow-list полів.
5. Play Console → Monetize → Products: створіть одноразовий non-consumable
   `quietcamp_pro`, активуйте purchase option, налаштуйте license testers.
   Ціна приходить тільки з Play ProductDetails. Клієнт не містить ціни-заглушки.
6. Pub/Sub: налаштуйте RTDN і authenticated push на `/v1/play/notifications`.
   `QC_PUBSUB_AUDIENCE` має збігатися з audience JWT, а
   `QC_PUBSUB_SERVICE_ACCOUNT_EMAIL` — із виділеною push-ідентичністю.
   Перевіряються Google signature, issuer/audience/expiration та verified email.
   Повідомлення про купівлю спричиняє повторний запит Play, а не прямий grant.
7. Планувальник сервера має щонайменше щодня запускати
   `python Server/service.py reconcile --hours 48`. Перекриття вікон навмисне;
   повторне відкликання безпечне. Після простою перевірте до 30 днів і всі сторінки
   Voided Purchases API. API може мати затримку; RTDN не замінює звірку.
8. Внесіть HTTPS `/v1/purchases/verify` у owner.local.json. Пройдіть реальні
   Android-сценарії до підтвердження готовності.

## Право на Pro

Backend звіряє package/product із серверними allow-list значеннями та перевіряє
purchase token через `purchases.productsv2.getproductpurchasev2`. Для PURCHASED
спочатку зберігається серверний grant, потім надсилається acknowledgment через
`purchases.products.acknowledge`. PENDING не дає доступу й не підтверджується.
Повернення/скасування/voided token створюють незворотний Revoked для цього token;
нова покупка має новий token. SQLite upsert не дозволяє позитивній відповіді,
що запізнилася, перезаписати відкликання.

Таблиця містить SHA-256 token, product, state, час останньої перевірки; сирі
tokens не зберігаються на сервері й не виводяться в помилках. Клієнт передає token
по TLS, коли Play повернув покупку; зберігає історію tokens у приватному Android
SharedPreferences для повторної перевірки після refund. Це чутливий доказ покупки,
який очищується також через видалення локальних даних у грі. Він не є секретом
усередині збірки й не має абсолютного захисту на модифікованому пристрої;
його не можна логувати або надсилати в Analytics. Сервер не має облікових записів
гравців: доказом є Google purchase token. Вкрадений token може бути повторно
використаний модифікованим клієнтом; тут немає обіцянки абсолютного захисту.
Для прив'язки до людини/акаунта потрібна окрема автентифікація та recovery-модель.

Клієнт отримує право на 24 години, перевіряє на старті, при поверненні та кожні
15 хвилин активної роботи. Без мережі чинне право працює до завершення строку;
після цього потрібна перевірка. Серверне відкликання почне діяти на клієнті після
успішної звірки або завершення строку. Зміна локального годинника/модифікований
клієнт можуть обійти локальні обмеження. TLS перевіряється системою; підписаних
серверних квитанцій у цьому варіанті немає. AES із ключем у клієнті не застосовано.

Історичні локальні Pro-збереження зберігають поведінку в локальному прототипі.
При підключенні перевіреного Billing-конфігу потрібне справжнє серверне право.
Баланс життів і підказок при завершенні права не стирається.

## Операційна статистика

Вимкнена з обох боків за замовчуванням. Потрібні незалежно підтверджена правова
підстава, опублікований опис і `QC_METRICS_LEGAL_BASIS_REVIEWED=true` на сервері.
Якщо підстава вимагає батьківської авторизації, цей механізм вмикати не можна:
батьківська верифікація не реалізована й не потрібна для звичайної гри.

Allow-list: `name` (`level_result`, `technical_failure`, `frame_time`), `bucket`
0..5, `count` 1..100. Немає user/install/session ID, віку, рівня, вільного тексту,
точного часу чи purchase token. Поточний клієнт підключає лише результати рівня
для Under13, тримає обмежені агрегати в пам'яті, надсилає при background лише
після 10 подій. Зміна віку очищує чергу. Перезапуск її не відновлює.
Сервер зберігає денні суми до 30 днів; очищення виконується при наступному ingest.
Для неактивного сервера додайте окрему щоденну retention-задачу.

IP і транспортні метадані все одно доступні мережі та ingress: це не твердження
«анонімно». Підтвердіть налаштування ingress, регіон зберігання, правову підставу,
строки видалення й фактичний Android-трафік до ввімкнення.

Для entitlement hashes визначте строк зберігання за потребами обліку/повернень
і правами користувача; автоматичного юридично визначеного строку тут немає.
Видалення terminal revocation може дозволити старий token знову пройти перевірку,
якщо зовнішнє джерело застаріле: політику видалення погодьте з власником.
